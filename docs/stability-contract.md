# AIIR 1.0 Stability Contract

> **Status: DRAFT** — This document defines the stability guarantees that will
> take effect when AIIR reaches version 1.0.0. Until then, it represents
> intent, not a binding promise.

---

## What 1.0 means

AIIR 1.0 is a commitment to a stable core. It means:

1. The receipt format is frozen.
2. Verification semantics are frozen.
3. Policy presets are supported interfaces.
4. Downstream tools can build on AIIR without fearing near-term breakage.

It does **not** mean "feature complete" or "enterprise platform." It means the
wedge is reliable: verifiable AI involvement evidence for git-centric workflows.

---

## Stable core (frozen at 1.0)

These interfaces are subject to [Semantic Versioning 2.0.0](https://semver.org/).
Breaking changes require a major version bump (2.0.0).

### Receipt format

- **Schema**: `aiir/commit_receipt.v2` — field names, types, and required/optional
  status are frozen. New optional fields may be added (minor version).
- **Content addressing**: The canonical JSON serialization algorithm and SHA-256
  hash derivation are frozen. A receipt generated by 1.0 will verify correctly
  with any future 1.x release.
- **Receipt ID format**: The `g1-` prefix and 32-hex-char derivation from the
  content hash are frozen.

### Verification semantics

- **`aiir --verify`**: The exit codes (0 = valid, 1 = invalid, 2 = error) and
  verification algorithm are frozen.
- **`aiir --verify-signature`**: Sigstore signature verification semantics
  (including `--signer-identity` and `--signer-issuer` pinning) are frozen.
- **`aiir --verify-release`**: Release-scoped verification and VSA emission
  semantics are frozen.

### Policy presets

- **Three named presets**: `strict`, `balanced`, `permissive` — their field
  names and default values are frozen. New fields may be added with safe defaults.
- **Policy file format**: `.aiir/policy.json` schema is frozen. New optional
  keys may be added.
- **Enforcement levels**: `warn`, `soft-fail`, `hard-fail` semantics are frozen.

### CLI interface

- **Core flags**: `--pretty`, `--json`, `--jsonl`, `--verify`, `--sign`,
  `--range`, `--output`, `--ledger`, `--init`, `--check`, `--policy`,
  `--verify-release`, `--emit-vsa`, `--explain` — their behavior is frozen.
- **Exit codes**: 0 (success), 1 (verification failure / policy violation),
  2 (runtime error) — frozen.
- **Output format**: Human-readable `--pretty` output and JSON/JSONL output
  structure are frozen.

### Detection

- **Detection method**: `heuristic_v2` — the detection algorithm name and
  `ai_attestation` field semantics are frozen. The set of detected signals
  may grow (minor version).
- **Authorship classes**: `human`, `ai_assisted`, `bot`, `ai+bot` — frozen.
  New classes require a minor version bump.

### Ledger

- **Format**: `.aiir/receipts.jsonl` append-only JSONL format is frozen.
- **Index**: `.aiir/index.json` structure is frozen. New optional fields may
  be added.
- **Deduplication**: Same-commit idempotency guarantee is frozen.

## Extension surface (not frozen)

These interfaces may change in minor or patch releases without a major
version bump. They are useful but should not be treated as stable contracts.

### Extensions field

- `extensions` in receipts is explicitly not part of the content hash.
  Fields within `extensions` (agent attestation, namespace, review metadata)
  may be added, changed, or removed in minor versions.

### MCP server

- Tool names and parameter schemas may change. Consumers should handle
  unknown fields gracefully.

### GitHub Action / GitLab CI component

- Input names and default values may change in minor versions.
  Pin to a specific version tag or SHA for stability.

### VS Code extension

- Commands, views, settings, and UI may change freely. The extension
  version follows its own release cadence.

### Analytics, dashboards, and Hub features

- Optional, networked features are explicitly experimental and may be
  added, changed, or removed without notice.

### Detection signal list

- New AI-tool signals may be added in patch releases. The overall detection
  method and field semantics are stable, but the specific patterns matched
  are not frozen.

## Compatibility policy

| Change type | Version impact | Example |
|-------------|---------------|---------|
| Add optional receipt field | Minor (1.x) | New `extensions.editor_session` key |
| Add detection signal | Patch (1.x.y) | Detect a new AI coding tool |
| Add policy field (safe default) | Minor (1.x) | New `require_review` field |
| Change canonical JSON algorithm | **Major (2.0)** | Different hash for same receipt |
| Remove required receipt field | **Major (2.0)** | Drop `provenance` from core |
| Change verification exit codes | **Major (2.0)** | Exit 3 for new error class |
| Change authorship class values | Minor (1.x) | New `ai_reviewed` class |

### Forward compatibility

A receipt generated by AIIR 1.0.0 will verify correctly with any AIIR 1.x.y
release. A receipt generated by 1.2.0 will verify with 1.0.0 if it uses only
1.0.0-era fields (unknown fields are ignored during verification).

### CBOR encoding

The canonical CBOR encoding is a secondary format tied to the primary JSON
format. CBOR round-trip fidelity (JSON → CBOR → JSON produces identical content
hash) is frozen at 1.0.

## Pre-1.0 checklist

AIIR should not be tagged 1.0.0 until all of the following are true:

- [ ] Receipt format, verification, and policy semantics are documented and tested
- [ ] 100% test coverage maintained for 4+ consecutive releases
- [ ] VS Code extension first-run path works in under 5 minutes
- [ ] Three adoption guides published (solo developer, OSS maintainer, security team)
- [ ] Trust page published with "proves / doesn't prove / verify independently"
- [ ] At least 2 public reference deployments (not just dogfood)
- [ ] `pyproject.toml` classifier updated from `4 - Beta` to `5 - Production/Stable`
- [ ] This document moved from DRAFT to ACTIVE status
- [ ] CHANGELOG.md entry documents the stability contract
