# GitLab AI Provenance Evidence

> **Status:** draft v0 — producer-side artifact only.
> No hosted service required. No Orbit integration in this document.

## What this is

A **GitLab AI provenance evidence artifact** is a structured JSON file that a
GitLab CI job produces and uploads as an ordinary pipeline artifact. It records,
for a specific merge-request pipeline run:

- which GitLab project, merge request, pipeline, and job produced it
- which commit and changed files it covers
- whether AI involvement was declared in that commit's metadata
- which AI signals were found in the declared metadata
- a reference to an AIIR receipt (if one was generated), along with its
  verification status

The artifact schema identifier is `gitlab_ai_provenance_evidence.v0`.

This is a **producer-owned artifact**. It is useful before any downstream
integration exists. A team can start generating it today and query it with
ordinary CI artifact APIs, `jq`, or any JSON-aware tool.

---

## Why produce it before any integration exists

Provenance evidence is most valuable when it accumulates over time. Starting
to produce it now means:

- You have a record of AI involvement for every MR pipeline, queryable
  immediately with standard GitLab artifact APIs.
- Future tooling — whether GitLab-native, Orbit-based, or your own — can
  consume a stable artifact format rather than reconstructing history.
- The artifact is self-describing: schema version, subject, and verification
  status are all explicit fields.

---

## How GitLab CI produces it

The artifact is generated by a dedicated CI job that runs in the
`merge_request_event` pipeline source. The job:

1. Installs AIIR (zero runtime dependencies, stdlib only).
2. Runs `aiir` over the MR commit range to generate a commit receipt.
3. Assembles the `gitlab_ai_provenance_evidence.v0` envelope from the receipt
   output and GitLab CI environment variables.
4. Uploads `aiir-evidence.json` as a standard GitLab job artifact.

See [`templates/gitlab-aiir-evidence.yml`](../../templates/gitlab-aiir-evidence.yml)
for a ready-to-include CI template.

### Minimal pipeline inclusion

```yaml
include:
  - local: templates/gitlab-aiir-evidence.yml
```

Or, if you mirror AIIR to your own GitLab instance, pin a ref that actually
contains this template. The evidence template first shipped in merge commit
`9f0223e5`; the `v1.5.1` tag predates it and will return 404. Pin an immutable
commit SHA (best for external trust) or a release tag that includes the template:

```yaml
include:
  - project: 'your-group/aiir'
    ref: '9f0223e59f3d54b148f09d93f3be5a01c3a26529'
    file: '/templates/gitlab-aiir-evidence.yml'
```

## Field reference

### Top-level fields

| Field | Type | Description |
|-------|------|-------------|
| `schema` | string (const) | Always `gitlab_ai_provenance_evidence.v0` |
| `subject` | object | Identifies the GitLab pipeline context |
| `change` | object | Identifies the commit and diff |
| `provenance` | object | AI involvement declaration and signals |
| `receipt` | object | AIIR receipt reference and verification status |
| `extensions` | object | Optional forward-compatibility fields |

### `subject` — GitLab SDLC context

Maps to familiar GitLab concepts:

| Field | GitLab concept |
|-------|---------------|
| `project_full_path` | Project (namespace/name) |
| `merge_request_iid` | Merge Request (internal ID) |
| `pipeline_id` | Pipeline |
| `pipeline_sha` | The commit SHA the pipeline ran on |
| `job_id` | Job |
| `job_name` | Job name (e.g. `aiir_evidence`) |

`subject.kind` is fixed to `gitlab.merge_request_pipeline` in v0.

### `change` — commit and diff

| Field | Description |
|-------|-------------|
| `commit_sha` | Full 40-character git commit SHA |
| `diff_hash` | `sha256:` + SHA-256 of the full diff (matches AIIR receipt field) |
| `files_changed` | List of changed file paths, sourced from the AIIR receipt's `commit.files` array. Empty when file paths were redacted (`commit.files_redacted`) or capped (`commit.files_capped`); redaction state is recorded under `extensions`. Note: the AIIR receipt also has a `commit.files_changed` field, but that is an **integer count** — it is not used here. |

### `provenance` — AI involvement

| Field | Description |
|-------|-------------|
| `declared_ai_involvement` | `true` if AIIR detected any AI signal in declared commit metadata |
| `detection_boundary` | Always `declared-metadata-only` in v0 |
| `signals` | List of raw signal strings found (e.g. `"Co-authored-by: Claude"`) |

`detection_boundary: declared-metadata-only` is a first-class field, not a
footnote. See [What AIIR verifies and does not verify](#what-aiir-verifies-and-does-not-verify).

### `receipt` — AIIR receipt reference

| Field | Description |
|-------|-------------|
| `producer` | Always `AIIR` |
| `producer_version` | AIIR version that generated the receipt (e.g. `1.5.1`) |
| `mode` | Always `declared-ai-receipt` in v0 |
| `receipt_id` | AIIR receipt ID (`g1-` prefix, content-addressed) |
| `content_hash` | `sha256:` + SHA-256 of the receipt core |
| `verification_status` | `valid`, `invalid`, or `unverified` |
| `verified_at` | RFC 3339 timestamp of verification — **omitted when `verification_status` is `unverified`** |
| `signed` | Whether the receipt carries a Sigstore signature |

## What AIIR verifies and does not verify

### AIIR verifies

- **Declared metadata**: AI signals present in commit trailers, author fields,
  and commit message body (e.g. `Co-authored-by: Copilot`, `AI-assisted`).
- **Receipt integrity**: The `content_hash` in a commit receipt is a
  deterministic SHA-256 of the receipt core. Re-running `aiir --verify` on
  the same receipt file confirms nothing was altered.

  ```bash
  # Verify a single AIIR receipt file (documented CLI command):
  aiir --verify .aiir-receipts/<receipt>.json

  # Verify all receipts in the output directory (shell loop):
  for f in .aiir-receipts/*.json; do aiir --verify "$f"; done
  ```

  Note: `--verify` takes a **file** argument. Passing a directory is not
  supported. Use a shell loop to verify multiple receipts.

- **Sigstore signatures** (optional): When `--sign` is used in CI, the receipt
  carries a Sigstore bundle. `aiir --verify` checks the bundle against the
  Sigstore public-good transparency log.

### AIIR does not verify

- **Hidden AI usage**: Copilot inline completions, copy-paste from ChatGPT,
  agent-mode sessions that leave no commit trailer, or any AI involvement not
  declared in commit metadata.
- **Undeclared AI usage**: If a developer uses an AI tool but does not add a
  `Co-authored-by` trailer or equivalent signal, AIIR will not detect it.
- **Human intent**: AIIR records what was declared, not why.
- **Policy scoring**: AIIR does not assign risk scores or compliance grades.
  Policy evaluation is a separate concern (see
  [`templates/policy-balanced.json`](../../templates/policy-balanced.json)).
- **Enterprise control-plane logic**: No hosted service is required or implied.

> **Important:** The `detection_boundary: declared-metadata-only` field in
> every v0 artifact makes this limitation machine-readable, not just a
> documentation footnote.

## Verification status in the envelope

The `receipt.verification_status` field has three possible values:

| Value | Meaning |
|-------|---------|
| `valid` | AIIR verified the receipt content hash (and signature, if present) |
| `invalid` | Verification failed — receipt was altered or signature is invalid |
| `unverified` | No verification was performed in this pipeline run |

When `verification_status` is `unverified`, the `verified_at` field is omitted
(or null). The CI template in this pack sets `unverified` by default because
the exact AIIR command to verify the `gitlab_ai_provenance_evidence.v0`
envelope as a whole is not yet documented.

> **TODO:** Document the AIIR CLI command (or a companion script) that reads
> `aiir-evidence.json`, re-derives the `content_hash` from the underlying
> receipt, and sets `verification_status` to `valid` or `invalid`. Until that
> command exists, the envelope is produced with `unverified` status and the
> underlying AIIR receipt file (in `.aiir-receipts/`) can be verified
> independently with `aiir --verify .aiir-receipts/<receipt>.json` (one file
> at a time) or via a shell loop: `for f in .aiir-receipts/*.json; do aiir --verify "$f"; done`.

## Mapping to GitLab SDLC concepts

This artifact uses ordinary GitLab CI metadata. The fields map to concepts
every GitLab user already knows:

| Artifact field | GitLab concept | Where to find it |
|----------------|---------------|-----------------|
| `subject.project_full_path` | Project | `CI_PROJECT_PATH` |
| `subject.merge_request_iid` | Merge Request | `CI_MERGE_REQUEST_IID` |
| `subject.pipeline_id` | Pipeline | `CI_PIPELINE_ID` |
| `subject.pipeline_sha` | Pipeline commit | `CI_COMMIT_SHA` |
| `subject.job_id` | Job | `CI_JOB_ID` |
| `change.commit_sha` | Commit | git HEAD |
| `change.files_changed` | Changed file paths | AIIR receipt `commit.files` array (empty if redacted) |

Security scan results (Findings, Vulnerabilities) are separate GitLab data.
A future reader could compare them with this artifact — for example, to ask
whether AI-declared MRs that touched certain files also had security findings.
That comparison is a read-side join on existing GitLab data; it is not a new
field in this v0 artifact.

## GitLab and Orbit positioning

Orbit may be an eventual reader or query surface for this artifact type.
**This document does not integrate with Orbit.** It does not define an Orbit
ontology, adapter, ingestion path, or graph schema.

For public context on Orbit's direction for Duo Agent Platform session
attribution on commits, see
[gitlab-org/orbit/knowledge-graph#800](https://gitlab.com/gitlab-org/orbit/knowledge-graph/-/issues/800).
That issue tracks Orbit ingestion work; this artifact is a producer-side
complement that could be consumed by such ingestion in the future.

## Non-goals

- No changes to Orbit core or GitLab Observability.
- No claim to detect undeclared AI usage.
- No hosted service requirement.
- No mandatory signing (signing is optional via `--sign`).
- No policy scoring or enterprise control-plane logic.
- No Orbit ontology, node/edge definitions, or ingestion design.

---

## AIIR is one possible producer

AIIR is one tool that can produce this artifact. Any tool that:

- runs in GitLab CI,
- reads commit metadata for AI signals,
- and writes a JSON file conforming to `examples/gitlab/aiir-evidence.schema.json`

is a valid producer. The schema is the contract; AIIR is a reference
implementation.
